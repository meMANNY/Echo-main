CRITICAL ARCHITECTURAL FACT — THE GUI THREAD RULE
--------------------------------------------------
This is the Phase 5 equivalent of Phase 4's "two roles in one process"
fact. Internalize it before writing a line of UI:

  ONLY the thread that created a widget may touch it. In Qt that is
  the MAIN thread (the one running QApplication.exec_()). Your
  heartbeat thread, peer-listener workers, and download workers must
  NEVER call a widget method, set a label, or append to a text box.
  Doing so doesn't always crash immediately — it corrupts state and
  crashes LATER, somewhere unrelated, which is far worse.

The sanctioned crossing is the SIGNAL/SLOT mechanism: a background
thread emits a signal (thread-safe), Qt queues it, and the connected
slot runs on the GUI thread where touching widgets is legal. Every
piece of data that originates on a background thread (a heartbeat
update, an inbound chat, a progress tick) crosses into the UI through
exactly one doorway: a pyqtSignal.

Echo has an advantage here that Drizzle threw away. Drizzle fused
transport and UI into one 2415-line file (DrizzleMainWindow.py) glued
together by ~10 module globals. Your ClientCore is already Qt-free.
Phase 5's central design job is ONE new class — a thin adapter that
owns the core, exposes signals, and forwards core events into them.
Keep that seam clean and the rest of Phase 5 is layout work.

2. It teaches EVENT-DRIVEN programming for real. Phase 4 was

STEP 5.1.2 — The CoreAdapter (the design centerpiece)
--------------------------------------------------------------------------------

One new class, client/adapter.py (or inside app.py to start):

  class CoreAdapter(QObject):
      peers_changed      = pyqtSignal(dict)   # uname -> last_seen
      message_received   = pyqtSignal(dict)   # Message TypedDict
      notification       = pyqtSignal(str, str)             # title, body
      transfer_progress  = pyqtSignal(object)               # 4.6 struct
      transfer_request   = pyqtSignal(object, object)       # 4.7 consent
      connection_lost    = pyqtSignal(str)                  # reason

It OWNS a ClientCore and a PeerListener (and, per 5.3.8, the share-folder
watcher), and does three jobs:

  (a) FORWARD EVENTS OUT. Give ClientCore plain-Python callback hooks
      (self.on_peers_changed, self.on_message, ...) that default to
      None. Core calls them (guarded: `if self.on_message: ...`) at
      the exact points where it currently only logs — end of
      _update_online_peers, inside add_message_to_history (receive
      path), inside notify(). The adapter sets each hook to a
      function that emits the matching signal. Emitting a signal from
      a non-GUI thread is SAFE — that is the entire point; Qt sees the
      receiver lives on the GUI thread and queues the call.
      Core stays importable without Qt; headless tests still run.
      NOTE (post-Improvement-A): connection teardown now happens inside
      ServerConnection, not in a core method you can drop a hook into.
      For the connection_lost signal (5.3.6), add an on_connection_lost
      hook that fires the moment `connected` goes False — cleanest is a
      callback ServerConnection invokes on teardown, surfaced through
      core so the adapter still only ever talks to core.

  (b) RUN BLOCKING CALLS OFF THE GUI THREAD. connect_to_server(),
      register(), browse(), search(), publish_share_data() all block
      on a network round-trip. Called directly from a button handler
      they freeze the window for up to the socket timeout. Drizzle
      makes exactly this mistake: it connects AND registers on the GUI
      thread inside the window constructor (DrizzleMainWindow.py:
      1278-1304) — with a slow server the app white-screens on
      launch. Give the adapter a small "run in worker, deliver result
      via signal" helper (QThreadPool + QRunnable is enough) and route
      every user-initiated core call through it.

  (c) BE THE ONLY QT<->CORE TOUCHPOINT. Widgets talk to the adapter;
      the adapter talks to the core. If a widget ever imports
      client.core directly, you are rebuilding Drizzle.

Decision (mirrors Phase 4 Q1): adapter by COMPOSITION, not making
ClientCore inherit QObject. Inheriting would drag Qt into every
headless test and tie core's lifetime to Qt's. Composition keeps the
dependency arrow pointing one way: adapter -> core, never core -> Qt.

STEP 5.1.3 — Window switching
--------------------------------------------------------------------------------

First-run flow: StartWindow (username) -> BasicConfigWindow (server IP,

having each window construct the next and close itself
(StartWindow.py:93-97 onContinue). It works; keep it, but pass the

--------------------------------------------------------------------------------
STEP 5.3.8 — Share auto-rescan (rescan-on-change)
--------------------------------------------------------------------------------
This is Phase 4 Improvement F, deferred to here because it only pays off
with a UI: keep the server's index of YOUR share in sync automatically
when files appear/disappear/change under SHARE_FOLDER_PATH, instead of
making the user click "Share/Rescan" after every edit. Drizzle has
nothing like it — a stale share tree until manual re-publish is exactly
the kind of paper cut this removes.

MECHANISM (recommended: watchdog observer)
  - The adapter owns a watchdog Observer watching SHARE_FOLDER_PATH
    recursively. Its event handler runs on watchdog's OWN thread, so it
    obeys the same rule as the heartbeat/listener threads: it touches NO
    widgets and calls NO locked core method directly. It does exactly one
    thing — emit a thread-safe adapter signal (share_changed).
  - DEBOUNCE, or you will republish dozens of times per file copy. A
    single "paste a folder in" fires a storm of created/modified events.
    The share_changed slot (GUI thread) (re)starts a single-shot
    QTimer(QUIET_PERIOD ~2s); only when the timer finally fires — i.e.
    ~2s after the LAST event — does it kick ONE publish_share_data()
    through a QThreadPool worker (never on the GUI thread; it locks the
    server connection and does a round-trip). A burst collapses to one publish.
  - publish_share_data already republishes the WHOLE tree and the server
    REPLACES the record (UPDATE_SHARE_DATA). Do NOT compute and send
    incremental deltas — whole-tree republish is idempotent, cheap at LAN
    share sizes, and is exactly what your manual Share button does.

UI FEEDBACK (small, optional, worth it)
  - A brief status cue ("Updating share..." -> "Share updated") so the
    user sees the automatic action; a silent background republish that
    occasionally fails is worse than a visible one.
  - If the user is currently viewing their OWN share tree, re-render it
    after a successful republish (adapter emits share_republished -> slot
    redraws). Viewing someone else's tree: do nothing.

MANUAL COMPANION (keep it)
  - The RIGHT pane's Import File/Folder and Share buttons (5.2.3) stay.
    Auto-rescan is the hands-free path; the manual button is the "do it
    now, don't wait for the debounce" escape hatch and the fallback when
    the watcher is disabled. NICE SIMPLIFICATION: because the watcher
    catches any change under the share root, Import File/Folder no longer
    needs to call publish itself — dropping the file into the share dir
    triggers the same republish path.

FALLBACK (zero new dependency): a periodic rescan — a QTimer every N
seconds that runs publish_share_data in a worker (optionally only when a
cheap top-level mtime scan shows change). Simpler, no watchdog dep, but
laggy and wasteful. Prefer watchdog; fall back only if you don't want the
dependency (Q8). NOTE: watchdog is NOT in the Pipfile yet — adding it is
the one new dependency this feature costs.

PHASE 5.4 — QT THREADING
================================================================================

GOAL: Every blocking or long-running operation off the GUI thread, with
exactly one crossing mechanism (signals). You already built the hard
concurrency in Phase 4; this section is about not un-building it.

--------------------------------------------------------------------------------
STEP 5.4.1 — Decide the thread map (write it down)
--------------------------------------------------------------------------------
  GUI thread          — widgets, and nothing else.
  core heartbeat      — your existing plain daemon thread. KEEPS
                        running as-is; its callback -> adapter signal.
  PeerListener        — your existing accept loop + per-connection
                        workers. KEEP. Callbacks -> adapter signals.
  share watcher       — watchdog Observer thread (5.3.8), if enabled.
                        Emits share_changed -> adapter; a GUI-thread
                        debounce timer turns an event burst into ONE
                        pooled publish. Plain (non-Qt) thread, like the
                        two above.
  QThreadPool         — short-lived workers for user-initiated
                        blocking calls (connect/register/browse/
                        search/publish) and per-file transfers.

This intentionally REFINES the Phase 4 plan's "Phase 5 re-homes plain
threads into QThreads": with the adapter pattern there is no need to
re-home core's internal threads at all — a pyqtSignal emitted from a
plain threading.Thread is delivered queued to the GUI thread exactly
like one emitted from a QThread. Re-homing would churn working code
for zero behavioral gain. What DOES need Qt machinery is anything the
UI initiates and waits on — that's what the pool is for. (See Q3.)

--------------------------------------------------------------------------------
STEP 5.4.2 — The three Qt worker patterns (know all, use two)
--------------------------------------------------------------------------------
Drizzle demonstrates all three; learn to recognize them:
  1. QObject worker + moveToThread — HeartbeatWorker (281-327) is
     created, moved to a QThread, and started via
     thread.started.connect(worker.run) (1309-1315). Right for
     LONG-LIVED loops that emit repeatedly. You won't need it (your
     loops live in core), but this is THE canonical Qt pattern —
     understand why the worker must be constructed BEFORE moveToThread
     and why its slots then run on the new thread.
  2. QRunnable + QThreadPool — RequestFileWorker (925). Right for
     SHORT-LIVED, pooled jobs: downloads, one-shot server calls.
     This is your workhorse.
  3. Subclassing QThread and overriding run() — the pattern most
     tutorials teach and the least composable. Skip it.

--------------------------------------------------------------------------------
STEP 5.4.3 — The QRunnable-has-no-signals trap
--------------------------------------------------------------------------------
QRunnable does not inherit QObject, so it CANNOT declare pyqtSignals.
Drizzle's fix is the little Signals(QObject) bundle (895-922): each
runnable carries `self.signals = Signals()` and emits through it
(download_files connects them per-worker at 1508-1510). Copy this
pattern verbatim for your download workers — trying to put signals
directly on a runnable is a classic hour-loser.

--------------------------------------------------------------------------------
STEP 5.4.4 — Locks across the boundary
--------------------------------------------------------------------------------
Drizzle guards its server socket with a QMutex (server_socket_mutex,
e.g. 1487-1495 in download_files). You go one better: Improvement A is
already built — ServerConnection owns the socket + its lock, and every
exchange goes through request()/run(), so a caller CAN'T forget to lock
or touch the raw socket. Rules for Phase 5:
  - Do NOT add QMutex around adapter calls into core; ServerConnection
    locks itself. Double-locking the same logical resource from two
    layers is how UI deadlocks are born.
  - The GUI thread must never WAIT on that lock for long: it never
    calls core's server methods directly (workers do). That rule is
    what keeps a slow server from freezing paint.
  - Shared dicts written by workers and read by slots (e.g. progress
    structs) are fine when writes stay in the worker and the UI only
    reads snapshots delivered via signal payloads. Prefer passing the
    DATA in the signal over sharing the structure.

--------------------------------------------------------------------------------
STEP 5.4.5 — Shutdown ordering
--------------------------------------------------------------------------------
closeEvent: dump the progress journal, stop the share watcher
(observer.stop(); observer.join(), if enabled), stop() the PeerListener,
close the server socket, THEN accept the close. Your Phase 4 daemon
threads die with the process — but flush anything they might be
mid-writing first (the journal write must not race a dying transfer
worker; pause active transfers before dumping, like Drizzle's
dump_progress_data flow, 1358-1362 + app.py:46-51). GOTCHA: the watchdog
Observer is NOT a daemon thread — join it explicitly or it can keep the
process alive after the window closes.


================================================================================
IMPORTANT CONCEPTS TO LEARN IN THIS PHASE
================================================================================

  1. THREAD AFFINITY & THE GUI THREAD RULE
     Every QObject "lives on" one thread; widgets live on the main
     thread and may only be touched there. This is not a Qt quirk —
     Win32, Cocoa, GTK, Android all have the same rule. The portable
     lesson: UI toolkits are single-threaded state machines; you
     bring data TO them, never reach INTO them from workers.

  2. SIGNALS/SLOTS AS THREAD-SAFE MESSAGE PASSING
     A queued signal is a message dropped into the receiver thread's
     event queue — the same idea as your wire protocol, in-process.
     Understand the connection types: Direct (same-thread function
     call) vs Queued (cross-thread, marshalled) vs Auto (Qt picks by
     comparing threads at emit time). Auto is why "emit from a plain
     thread" just works.

  3. THE EVENT LOOP
     exec_() is a while-true dispatching events — paint, click, timer,
     queued slot. Block it for 300ms and the app feels sticky; for 5s
     and Windows greys the title bar. Every "app frozen" bug in Phase
     5 is something synchronous sneaking onto this loop. Same model as
     your server's select() loop: one dispatcher, many small handlers,
     nothing slow inline.

  4. WORKER PATTERNS & LIFETIMES
     moveToThread for long-lived loops, QThreadPool/QRunnable for
     short jobs — and the lifetime traps: a QThread garbage-collected
     while running crashes; a worker parented to a widget dies with
     it. Keep references (self.thread, self.worker) deliberately.

  5. RETAINED-MODE UI & DIFF-BASED UPDATES
     Widgets persist between updates (retained mode); you reconcile
     new data against existing widgets rather than rebuilding
     (update_online_status's set-difference diff). This is the exact
     mental model behind React/Flutter reconciliation — learn it here
     with 40 lines of Python and no framework magic.

  6. DATA-CARRYING WIDGETS vs MODEL/VIEW
     setData(Qt.UserRole, obj) glues your DirData to tree rows —
     simple, fine at LAN scale. Know what it trades away: QTreeView +
     QAbstractItemModel separates data from view for 100k-row
     scalability and testability. Use QTreeWidget now; be able to say
     WHY, and what you'd switch to.

  7. UI STATE MACHINES (CAPABILITY GATING)
     Enabled/disabled buttons, connecting/connected/disconnected
     banners — the UI mirror of "make illegal states unrepresentable".
     Design states first, then widgets: every button should be
     impossible to click when its preconditions don't hold.

  8. BACKPRESSURE IN THE UI
     A 100MB/s transfer emitting a signal per 16KB chunk = ~6400
     queued events/sec — the GUI drowns doing repaints. Throttle at
     the SOURCE: emit progress every N chunks or when percent moved by
     >= 0.1. Same throughput-vs-overhead trade-off as your chunk-size
     decision in 4.5, resurfacing one layer up.

  9. GRACEFUL DEGRADATION, UI EDITION
     Server death mid-session must produce a calm banner + disabled
     controls + a retry path — not a dialog storm from the heartbeat
     failing every 5 seconds. Coalesce repeated failures into ONE
     state change (that's what connection_lost as a signal gives you).


================================================================================
IMPROVEMENTS YOU CAN ADD BEYOND DRIZZLE
================================================================================

  A. THE ADAPTER SEAM (Qt-FREE CORE)
     Drizzle: transport welded into the window class, ~10 module
     globals, untestable without X11. Echo: ClientCore untouched, one
     CoreAdapter, headless tests keep passing. This is the single
     biggest architectural win and it is nearly free — you already
     built the hard half in Phase 4.

  B. NO GUI-THREAD NETWORKING, EVER
     Drizzle connects+registers on the GUI thread in the constructor
     (1278-1304) and freezes on a slow server. Route every core call
     through the worker helper from day one. Cheap discipline,
     dramatic perceived-quality difference.

  C. JSON PROGRESS JOURNAL, NOT PICKLES
     Drizzle pickles transfer_progress/dir_progress/progress_widgets
     (1255-1276, 1343-1356) — unreadable, version-fragile, and
     unpickling arbitrary files is an attack surface. Your 4.6.4 JSON
     journal already does this better; the UI just renders it.

  D. A VISIBLE CONNECTION STATE (5.3.6)
     Drizzle has none: server death = mystery offline-everyone. A
     status banner + reconnect button turns your Phase 4 teardown
     paths into a feature a reviewer can see.

  E. NO sys.exit() ERROR HANDLING
     Drizzle exits the process from inside the window constructor on
     connect failure (1331-1339). Every Echo failure should land in a
     dialog/banner with a retry, and the app survives.

  F. PROGRESS SIGNAL THROTTLING (concept 8)
     Drizzle emits per-chunk. Emit per-N-chunks; keep the UI fluid
     during fast LAN transfers.

  G. TRANSFER RATE / ETA IN THE PROGRESS ROW
     ALREADY HALF-DONE: Phase 4 Improvement G shipped, so TransferProgress
     now carries speed_bps + eta_seconds, computed (EMA-smoothed) in core.
     Phase 5's job is pure rendering — show them in the FileProgressWidget
     label. Put format_speed/format_eta in utils/helpers.py (next to
     convert_size), NOT in core — they're presentation.

  H. SHARE AUTO-RESCAN (5.3.8)
     Phase 4 Improvement F, realized here: watch SHARE_FOLDER_PATH and
     auto-republish (debounced) so a peer's browse reflects your file
     changes without anyone clicking Rescan. Drizzle leaves the index
     stale until manual re-publish. Costs one dependency (watchdog) or a
     periodic-timer fallback (Q8).

Pick 2-3 beyond A/B/E which you should treat as non-negotiable: (D) is
the highest demo value; (F) matters the moment you test on a real LAN;
(H) is a small, obviously-correct polish that shows the share staying
live without a manual step.


================================================================================
DECISIONS TO MAKE BEFORE STARTING PHASE 5
================================================================================

  Q1. QT DESIGNER OR HAND-CODED LAYOUTS?
      Recommended: hand-code. Drizzle's files are pyuic-style output
      (setupUi/retranslateUi, objectName soup) — fine to CRIB layouts
      from, miserable to maintain. Hand-coding nested QVBox/QHBox
      layouts for these window sizes is genuinely less work, and you
      learn the layout system. If EchoMainWindow's three-pane layout
      fights you, Designer for that ONE window is a legitimate assist.

  Q2. ADAPTER (COMPOSITION) OR ClientCore(QObject)?
      Recommended: composition adapter (5.1.2). Core stays Qt-free and
      headless-testable; verify_phase4.py keeps working forever, which
      is also your fastest bug-repro tool once the GUI exists.

  Q3. RE-HOME CORE'S THREADS INTO QTHREADS?
      Recommended: NO (refines the Phase 4 plan's assumption). Keep
      the heartbeat + listener as plain threads; signals emitted from
      them are delivered queued regardless. Use QThreadPool only for
      UI-initiated blocking calls and transfers. Less churn, same
      safety — but write down WHY, because "when do I actually need a
      QThread" is exactly the kind of question this project exists to
      answer.

  Q4. QTreeWidget OR QTreeView+MODEL?
      Recommended: QTreeWidget with Qt.UserRole data (matches Drizzle,
      right-sized for LAN shares). Note QTreeView as the scale answer.

  Q5. CHAT RENDERING: QTextEdit+HTML OR PER-MESSAGE WIDGETS?
      Recommended: QTextEdit + insertHtml. construct_message_html and
      LEADING_HTML/TRAILING_HTML already exist for it. Per-message
      widget lists look nicer but cost layout performance and time.

  Q6. WHEN TO FIRE DESKTOP vs IN-APP NOTIFICATIONS?
      Recommended: desktop (notify-py) only when the app is not the
      active window; in-app cues otherwise. All behind the existing
      notify()/signal seam, honoring show_notifications.

  Q7. STYLING SCOPE?
      Recommended: functional first; at most one QSS stylesheet pass
      at the end (Session 9). Styling before wiring is procrastination
      with screenshots.

  Q8. AUTO-RESCAN: watchdog OR periodic rescan? (5.3.8)
      Recommended: watchdog Observer with a ~2s debounce — event-driven,
      instant, no busy polling; the cost is one new dependency (watchdog,
      not yet in the Pipfile). Fall back to a periodic-timer rescan only
      if you want zero new deps and can accept the lag. Either way:
      debounce (coalesce event bursts), republish the WHOLE tree via a
      worker (never on the GUI thread), and re-point the watcher when
      share_folder_path changes.

HOW TO VERIFY PHASE 5 IS DONE
================================================================================

Run the Phase 3 server + TWO GUI clients (ideally two machines, same
caveats as Phase 4 verification).

  Test 1 — first-run flow: fresh ~/.Echo -> StartWindow -> config ->
  main window connected and registered; settings.json created; second
  launch skips straight to the main window and auto-connects.

  Test 2 — presence: both users appear in each other's list as online
  within HEARTBEAT_TIMER; kill one, the other's list greys the entry
  with a last-active timestamp within ONLINE_TIMEOUT; selection
  enables/disables Send/Refresh correctly.

  Test 3 — browse + search UI: selecting a user renders their tree
  (empty share -> placeholder, not error); File Info shows size via
  convert_size and "unverified" hash; search dialog finds a file with
  owner attribution, empty query -> no request, no-results -> calm
  message; Go-to-owner selects and browses. Auto-rescan (5.3.8): drop a
  new file into bob's share folder — bob clicks nothing; alice hits
  Refresh (browse is pull-based) within a second or two and the new file
  is there, proving bob's index auto-republished on the change.

  Test 4 — chat: bidirectional messages render with sender styling;
  history survives switching users; over-length input is blocked at
  the box; minimized window -> desktop notification (if enabled).

  Test 5 — transfers (needs 4.5/4.6 done): download file + folder
  with live progress bars and human-readable sizes; pause -> resume
  -> hash verifies; kill the app mid-download -> relaunch shows the
  PAUSED row from the journal -> resume completes. Direct transfer
  pops the consent dialog; accept lands the file, reject shows a
  clean message to the sender (4.7).

  Test 6 — THE FREEZE TEST (the one that grades your threading):
  during a large transfer, the window stays responsive (drag it,
  scroll chat, click around). Stop the server mid-session: banner
  flips to disconnected, no dialog storm, Reconnect works after the
  server returns. At no point does the OS mark the app "not
  responding".

Phase 5 is done when all six pass on two machines, verify_phase4.py
STILL passes headless (proof the core stayed Qt-free and unbroken), and
grep finds no PyQt5 import anywhere under client/core.py,
client/peer_listener.py, or client/server_connection.py.
